# تكليفات الفرق واحتساب الزيارة المشتركة

تنفيذ 26 سبتمبر 2026، بعد اعتماد السيناريو التالي: المندوب يستطيع الانتماء إلى RX1 وRX2 تحت مدير، وOTC تحت مدير آخر، داخل المحافظة نفسها. زيارة طبيب مشترك تُحتسب لكل التكليفات المطابقة، لكنها زيارة فعلية واحدة في إجمالي الشركة.

## المنفذ

- ترحيل إضافي `20260926010000_team_visit_attribution`: نطاق مناطق وأصناف وجهات لكل RepCycleTeamPeriod، وربط VisitTeamCredit بين الزيارة والتكليف، وأصناف VisitTeamProduct المحفوظة لكل احتساب.
- تكليف الفريق يحدد فترة ضمن سايكل الشركة؛ يمنع تداخل تكليفين لنفس المندوب والفريق، ويمنع تكليفات متزامنة بمحافظتين مختلفتين.
- إعداد النطاق يستعمل مناطق المندوب الموجودة، وأطباءه المسندين المطابقين لاختصاصات الفريق، والأصناف المشتركة بين تكليف المندوب والفريق. لا ينشئ طبيباً أو تصنيفاً أو هدف زيارات تخميناً. الصيدليات والمشافي المسندة تُطابق بالمناطق.
- هدف الزيارات يؤخذ من RepCycleTarget الموجود ويُحفظ في نطاق الفريق. عند عدة فترات لنفس الفريق والجهة في السايكل، لا يُضاعف المطلوب؛ يستخدم أعلى مطلوب محفوظ ويجمع الإنجاز. لا يوجد هنا إعداد مستقل جديد لهدف كل فريق.
- تسجيل الجولة يحفظ Visit واحدة لكل جهة ثم ينشئ روابط الاحتساب لكل تكليف مطابق في تاريخ الزيارة، بلا خطوة اختيار فريق في الواجهة. احتساب التكليف المشترك لا يتوقف على اختيار صنف بعينه؛ الأصناف المختارة تُعرض لكل مدير ضمن نطاق أصنافه فقط.
- الطلب المكرر بنفس clientRef يسترجع الجولة السابقة، ولا يضيف زيارة أو احتساباً جديداً، ولا يعيد تصنيفها إذا تغيرت التكليفات لاحقاً.
- مدير الفريق يحتاج الصلاحية وعضوية إدارة فعالة في الفريق ضمن شركته. صاحب الصلاحيات الوطنية يرى نطاق شركته فقط؛ ليس كل الشركات. الأدوار تُفحص عبر permission codes، لا اسم الدور.
- مسار زيارات الفريق يعرض visit ID نفسه للمديرين المعنيين، لكن أصنافاً مختلفة حسب النطاق. لا يرسل الملاحظة العامة أو تفاصيل فرق أخرى.
- pagination لزيارات الفريق مع cursor محصور في الفريق والسايكل، وحد أقصى 100 للصفحة.
- ملخص الشركة يعد Visit مباشرة. teamCredits مقياس مستقل وقد يزيد عن physicalVisits.
- استجابة dashboard تضيف rep.teams وتحتفظ بحقل rep.team السابق للتوافق. صفحة حسابي تعرض كل الفرق المتزامنة.

## APIs

جميع المسارات تحت `/api/v1`، محمية بـJWT.

### POST /management/team-assignments

الصلاحيات: `teams.manage` و`cycles.configure`. يستعمل organizationId من الجلسة، لا body الطلب.

```json
{
  "repCycleProfileId": "UUID",
  "teamId": "UUID",
  "areaIds": ["UUID"],
  "startsOn": "YYYY-MM-DD",
  "endsOn": "YYYY-MM-DD"
}
```

يتطلب وجود السايكل وتكليف المندوب والمناطق والجهات وتصنيفاتها واختصاصات الفريق وروابط الأصناف. يعيد ID فترة الفريق وعدد الجهات والأصناف. التعديل المباشر على نطاق سبق تفعيله مرفوض لحماية التاريخ؛ إدارة إنهاء التكليف وتعديل نطاق مستقبلي بواجهة إدارية ما زالت مرحلة لاحقة.

### GET /management/teams/:teamId/cycles/:cycleId/coverage

الصلاحية `analytics.view_team` مع عضوية مدير، أو `analytics.view_national` ضمن الشركة. يعيد الجهات والمندوبين والإنجاز والمطلوب والتغطية وعدد فترات التكليف غير المعدّة.

### GET /management/teams/:teamId/cycles/:cycleId/visits?limit=30&cursor=UUID

الصلاحية `visits.view_team` مع عضوية مدير، أو `visits.view_all` ضمن الشركة. يعيد الزيارات والأصناف التابعة للفريق فقط وnextCursor.

### GET /management/company/cycles/:cycleId/summary

الصلاحية `analytics.view_national`. يعيد physicalVisits وallocatedVisits وunallocatedVisits وteamCredits.

## البيانات السابقة

عند المراجعة وُجدت شركة واحدة، تكليف سايكل واحد، وفترة فريق واحدة، ولا روابط TeamSpecialty أو TeamProduct للفريق. لذلك:

- الترحيل أضاف الجداول فقط، ولم ينشئ فرق RX أو أسماء مديرين في بيانات التشغيل.
- لم يغيّر الزيارات القديمة ولم ينسبها تخميناً إلى فريق.
- تفعيل نطاق بمدة مختلفة ينشئ فترة صريحة جديدة ويحفظ تواريخ الفترة القديمة؛ اختُبر ذلك على قاعدة البيانات.
- النطاق القديم يبقى فعالاً للمندوب حتى إعداد نطاقات الفرق صراحة. بعد تفعيلها تعتمد قوائمه وتسجيلاته على نطاقات الفرق الفعالة في التاريخ المعني.
- زيارات بلا احتساب تظهر في إجمالي الشركة وunallocatedVisits، ولا تُعرض لمدير اعتماداً على مجرد اشتراك المندوب معه.
- لا توجد عملية backfill تلقائية. أي استكمال تاريخي يحتاج مراجعة تكليفات الفترة والمناطق والأصناف الأصلية.

## التحقق

- Prisma validate / migrate deploy / migrate status: ناجحة، الترحيل مطبق محلياً.
- TypeScript وNest build: ناجحان.
- Web ESLint وNext build: ناجحان.
- ستة اختبارات في أربع مجموعات، بينها اختبارات PostgreSQL الفعلية: ناجحة.
- الاختبار المعزول ينشئ شركتين ومديرين ومندوباً وثلاثة فرق ومناطق واختصاصات وأصنافاً مؤقتة داخل transaction ثم يلغيها بالكامل.
- يتحقق من ظهور نفس visit ID في RX1 وRX2 وOTC، وعزل أصناف أحمد وطارق، وثلاثة احتسابات مقابل زيارة واحدة للشركة، ورفض الشركة/الفريق/الجهة/التاريخ خارج النطاق، وتكرار الطلب، وتكرار تكليف الفريق، وثبات أصناف الاحتساب بعد تعديل روابط الفريق.
- اختبارات HTTP على التطبيق المحلي: 200 للمسارات المصرّح بها، 403 بلا صلاحية أو بلا عضوية الإدارة، و400 لمدخلات التكليف وlimit غير الصالحة.
- بقي تحذيرا any السابقان في RepDashboardService. اختبارات قاعدة البيانات تظهر كذلك تحذير pg عن الطلبات المتزامنة على connection واحدة؛ الاختبارات ناجحة لكنه يحتاج معالجة قبل ترقية pg الرئيسية.

## النطاق التالي، غير المنفذ هنا

هذه خطوة الباك وتكليفات الفرق، وليست اكتمال لوحات المدير وصاحب الشركة والسوبر أدمن. لم تُبنَ واجهات إدارة التكليفات أو الثيم أو خصائص الشركة أو الاشتراكات أو اعتماد الإجازات أو مهلة تعديل الجولة. لم تُجرَ اختبارات حمل تثبت 100 مستخدم متزامن لكل شركة.

القرارات المحفوظة للمرحلة التالية: سايكل موحّد افتراضياً؛ أولوية إعدادات صاحب الشركة؛ أدوار مرنة لكل شركة؛ ثيم وخصائص للشركة والخريطة مؤجلة؛ اتصال دائم؛ انتهاء الاشتراك يسمح بالعرض ويمنع الكتابة في الباك؛ اعتماد الإجازات يحدده إعداد صريح وليس كل مدراء المندوب تلقائياً.

## إعادة التحقق

من `apps/api`:

```sh
npx prisma migrate deploy --config prisma7.config.ts
npx prisma generate --config prisma7.config.ts
RUN_DB_TESTS=1 npm run test
npm run build
```

لا تشغّل seed لترقية البيانات الموجودة. المراجعة لم تتضمن أي تعديل للمشروع القديم.
